# Устройство burn

## Принципы

1. **Совместимость с прототипом.** C-версия читает и пишет то же, что bash-прототип: рецепты, `burn.conf`,
   профили, `/var/lib/burn`, `.pkg.tar.zst`, журнал. Её можно поставить на систему, собранную прототипом,
   и продолжить обновления.
2. **Без shell в рабочем цикле.** Программы запускаются напрямую (`fork` + `exec`, никогда `sh -c`); tar, zstd,
   SHA-256 и разбор ELF — внутри процесса. bash запускается только для функций рецепта (`do_*`, `*_extra`,
   `post_install`).
3. **Атомарность.** Файл пакета пишется рядом под временным именем и встаёт на место через `rename()`; база
   пакетов меняется после файлов; триггеры (`ldconfig`, `depmod`, файловые триггеры пакетов) собираются в
   очередь и выполняются один раз.
4. **Минимум зависимостей.** libc и libzstd. Скачивание — через `curl` или `wget` (сборка `make CURL=1` — через
   libcurl в процессе: HTTP/2, по `FETCH_JOBS` передач сразу, к одному серверу — потоками одного соединения;
   повторы, как у `curl --retry 3`; `burn --version` показывает версию libcurl), распаковка исходников — через
   `tar` и `unzip` (форматов исходников слишком много, чтобы тащить их внутрь), патчи — через `patch`,
   `strip` — из тулчейна.

## Модули

| Файл | Что делает |
|---|---|
| `src/util.c` | вывод (`==>`, `->`, `warning:`, `error:`), память, строки, векторы, пути, файлы |
| `src/spawn.c` | запуск программ: рабочий каталог, окружение, лог, захват вывода |
| `src/sha256.c` | SHA-256: переносимый C и SHA-NI на x86-64 (выбирается по cpuid; `BURN_SHA256=c` — только C) |
| `src/vercmp.c` | сравнение версий в порядке `sort -V` (GNU filevercmp из coreutils ≥ 9) |
| `src/shparse.c` | язык рецептов: разбор и вычисление верхнего уровня, без bash |
| `src/config.c` | значения по умолчанию, `burn.conf`, профили, цель (CHOST, CPU), `burn profile` |
| `src/recipe.c` | рецепты: поиск, загрузка, особенности, зависимости, источники, идентичность (`rid`) |
| `src/db.c` | база установленных пакетов, блокировка корня |
| `src/tar.c` | потоковое чтение zstd и tar (ustar, GNU, pax), проверка путей |
| `src/tarw.c` | запись пакета: tar байт в байт как `tar --sort=name --numeric-owner --owner=0 --group=0 --mtime --clamp-mtime`, сразу в zstd (потоки по числу CPU) |
| `src/elf.c` | ELF: `SONAME`/`NEEDED` (32/64 бита, оба порядка байт, по секциям или сегментам), LTO-объекты в `.a` |
| `src/root.c` | операции с файлами строго внутри корня (`openat2` + `RESOLVE_IN_ROOT`, кэш каталогов) |
| `src/pkg.c` | установка и удаление пакетов, сохранённые библиотеки, триггеры, запись в базу |
| `src/source.c` | источники: кэш, загрузка (`curl`/`wget`, по `FETCH_JOBS` сразу), проверка sha256, `fetch`, `checksum` |
| `src/cmd_recipe.c` | `search`, `info`, `query`, `lint` |
| `src/cmd_db.c` | `list`, `files`, `owner`, `hold`, `unhold`, `history`, `doctor` |
| `src/flags.c` | окружение сборки: тулчейн, флаги профиля и пакета, ccache, `buildid`, `SOURCE_DATE_EPOCH` |
| `src/deps.c` | зависимости: порядок сборки, циклы, «установлен и свежий» |
| `src/build.c` | сборка: источники, патчи, фазы и лог, чистка дерева, пакет; `build`, `unpack` |
| `src/buildtype.c` | типы сборки (autotools, make, cmake, meson, cargo, python, meta, custom) — сам burn, без bash |
| `src/shrun.c` | функции рецепта: `env.sh` для bash, вызов `do_*`, `*_extra`, `post_install` |
| `src/prelude.sh` | вводная часть для функций рецепта (`use`, `use_enable`, `bt_*`, …), встроена в бинарник |
| `src/cmd_pkg.c` | `install <файл>` и `install <рецепт>` (сборка по зависимостям, ABI-пересборка), `remove`, `rollback`, `clone` (сборки другого корня из кэша: порядок по зависимостям из его базы) |
| `src/update.c` | `sync`, `plan`, `update`: репозитории рецептов, план, сборка всего до применения, хуки, состояние |
| `src/snapshot.c` | снимок btrfs перед `update` и `burn snapshot`: ioctl ядра, без btrfs-progs |
| `src/spin.c` | сборки (spins): `spin add/remove/list/show`, их рецепты и особенности в поиске и `features`, `sync` и новые пакеты в `update` |
| `src/main.c` | командная строка |

Каждая команда сверяется с прототипом: `make proto` запускает обе версии на одном тестовом корне
(`tests/proto.sh`) — вывод, ошибки, код возврата, корень и кеш (пакеты байт в байт, логи сборки) должны
совпасть. Сборки там — на тестовых рецептах `tests/fixtures/recipes/bt-*` с исходниками из
`tests/fixtures/src`: все типы сборки, чистка, ошибки фаз, зависимости и циклы, ABI-пересборка; обновления — на
репозитории рецептов, который строит `tests/mkrepo.sh` (с фиксированными датами коммитов). Снимки btrfs у
прототипа были хуком, поэтому их проверяет отдельный тест на настоящей btrfs: `make check-btrfs` (loop-устройство)
или `make check-btrfs KERNEL=bzImage` — то же внутри маленькой виртуальной машины (`tests/qemu-btrfs.sh`), если в
ядре хоста нет btrfs.

## Язык рецептов

Рецепт остаётся файлом bash: при сборке bash исполняет его функции. Но верхний уровень рецепта (а также
`burn.conf` и профилей) — **статический**, и burn разбирает его сам, без запуска bash. Разрешено:

- присваивания `name=value`, `name+=value`, несколько на одной строке;
- массивы `name=(a b c)` и `name+=(…)`, на нескольких строках, с комментариями внутри;
- кавычки `'…'`, `"…"`, `$'…'` и экранирование `\`;
- подстановки `$v`, `${v}`, `${v:-x}`, `${v-x}`, `${v:+x}`, `${v+x}`, `${v#p}`, `${v##p}`, `${v%p}`, `${v%%p}`,
  `${v/p/r}`, `${v//p/r}`, `${v/#p/r}`, `${v/%p/r}`, `${v^^}`, `${v,,}`, `${v^}`, `${v,}`, `${#v}`,
  `${v:off:len}`, `${a[@]}`, `${a[*]}`, `${a[N]}`, `${#a[@]}`;
- фигурные скобки в элементах массива: `{001..020}`, `{a,b}`;
- функции `name() { … }`: тело не разбирается (его исполнит bash), закрывающая `}` стоит в начале строки;
- `unset имя…`, `export имя[=значение]…`, в профилях — `inherit имя`.

Всё остальное на верхнем уровне — `if`, `for`, `$(…)`, `$((…))`, вызовы программ — ошибка разбора с номером
строки: логике место в функциях. Поэтому рецепт читается за микросекунды, а его метаданные не зависят от машины.
Обращение к неустановленной переменной — ошибка, как `set -u` в прототипе.

Смысл каждой конструкции — ровно как в bash (`nounset`, `nullglob`, `extglob`, как запускал рецепты прототип):

- раскрытие путей не делается, поэтому `*`, `?` и `[…]` без кавычек в элементе массива — ошибка (bash искал бы
  файлы в текущем каталоге и с `nullglob` молча выбросил бы элемент); в кавычках — обычные символы;
- `~` и `~/…` в начале слова, а в присваиваниях ещё и после `:`, — это `$HOME`;
- `export имя` до присваивания помечает будущую переменную, `unset` скрывает и переменные конфига, и окружение;
- рецепт разбирается поверх конфига и профиля: их переменные видны, а изменения остаются в рецепте.

Совпадение с bash проверяет `tests/shcompat.sh` (часть `make check`): набор случаев в `tests/sh/` и, с
`make check RECIPES=…/CleanLinux-Recipes/packages`, каждый рецепт репозитория — переменные и функции после
разбора должны быть те же, что после `source` в bash. Ошибочные конструкции из `tests/sh/err/` должны давать
ожидаемое сообщение.

Списки патчей вида «001…020» пишутся фигурными скобками, а версия выводится из числа элементов:

```sh
_patches=({001..020})
version=$_basever.${#_patches[@]}
patches=("${_patches[@]/#/bash${_basever/./}-}")
```

### Split-пакеты

Одна сборка может дать несколько пакетов: `split=(имя…)` перечисляет дополнительные пакеты рецепта. Каждый
забирает из `DESTDIR` то, что совпало с его шаблонами, и имеет свои метаданные; переменные split-пакета
называются по его имени, где каждый символ вне `[A-Za-z0-9_]` заменён на `_`:

```sh
name=gcc
depends=(glibc binutils gcc-libs zlib-ng zstd)   # компилятору нужны его библиотеки
split=(gcc-libs)
summary_gcc_libs="GCC runtime libraries: libgcc_s, libstdc++, libatomic, libgomp"
depends_gcc_libs=(glibc)
files_gcc_libs=(usr/lib/libgcc_s.so.1 'usr/lib/libstdc++.so.6' 'usr/lib/libstdc++.so.6.*[0-9]')
```

- `files_КЛЮЧ` (обязателен) — шаблоны glob относительно `DESTDIR` (в кавычках: язык рецептов не раскрывает
  пути); совпавшие файлы и каталоги целиком переезжают в пакет после чистки (шаг 4 сборки). Шаблон без
  совпадений — предупреждение (такой файл может не собираться на другой архитектуре), split без единого
  файла — ошибка;
- `summary_КЛЮЧ` (обязателен), `depends_КЛЮЧ`, `backup_КЛЮЧ`; `license_КЛЮЧ` — если не задан, лицензия
  рецепта; версия, release, особенности, `rid` и `buildid` — общие для всех пакетов рецепта;
- имя split-пакета работает везде, где имя рецепта: `install`, `info` (`split of`), `search`, `query`
  (`summary`, `depends`, `license`, `backup`, `files` — свои), зависимости других рецептов. Чтобы его собрать,
  нужно то же, что рецепту (его `depends` и `makedepends`), а свои пакеты рецепту для сборки не нужны никогда —
  ни в порядке сборки, ни в `buildid`;
- в `meta` split-пакета есть `base=<рецепт>`. Файлы переходят между пакетами одного рецепта при обновлении без
  конфликта (новый владелец забирает их у старого: `gcc-libs takes over N file(s) from gcc`), а SONAME, который
  ушёл из одного пакета, но есть в другом установленном, не считается потерянным — пересборки нет;
- `update` собирает рецепт один раз и ставит все его установленные пакеты; `--rebuild` и ABI-пересборка тоже
  собирают его один раз за команду.

`lint` проверяет имена split-пакетов (не совпадают с рецептом и с другими рецептами), `files_` и `summary_`,
зависимости `depends_`.

## Конфиг и профили

Порядок: значения по умолчанию → `$ROOT/etc/burn/burn.conf` → `-c FILE` (`$BURN_CONFIG`) → профиль → снова
конфиг (настройки пользователя сильнее профиля) → командная строка.

Профиль описывает только железо и ищется как `ИМЯ.profile` или `devices/ИМЯ.profile` в `$BURN_PROFILE_DIR`,
`$ROOT/etc/burn/profiles`, рядом с бинарником (`profiles/`, `../share/burn/profiles`) и в
`/usr/share/burn/profiles`. `inherit имя` подключает другой профиль. Профиль тоже статический и машину не
опрашивает: burn определяет её сам и передаёт профилю `HOST_ARCH` и `HOST_VIDEO_CARDS` (драйверы из
`/sys/class/drm`; переменная окружения важнее). Поэтому `native.profile` — это просто:

```sh
inherit base
CARCH=$HOST_ARCH
CPU_FLAGS=native
VIDEO_CARDS=$HOST_VIDEO_CARDS
```

`--target` без `-p`: если архитектура цели не совпадает с машиной, берётся профиль `generic-<arch>`.

Кроме флагов процессора профиль описывает железо устройства — эти переменные читают рецепты ядра, драйверов
и firmware:

| Переменная | Что это |
|---|---|
| `VIDEO_CARDS` | драйверы GPU: `amd intel nouveau freedreno panfrost v3d lima etnaviv virgl` (libdrm, Mesa, ядро) |
| `KERNEL_CONFIG` | полный конфиг ядра вместо defconfig архитектуры |
| `KERNEL_FRAGMENT` | фрагмент конфига ядра устройства, накладывается последним |
| `KERNEL_CMDLINE` | параметры ядра устройства (пакет `hardware` кладёт их в `/usr/lib/kernel/cmdline.d/`) |
| `FIRMWARE` | firmware устройства: пути внутри `/usr/lib/firmware` (каталоги или начала имён); пусто — всё |
| `MODULES` | модули, которые загружаются при старте (`modules-load.d`) |
| `QUIRKS` | каталог с quirks устройства: дерево `/usr/lib` (`udev/rules.d`, `udev/hwdb.d`, `modprobe.d`, `sysctl.d`, …) |
| `BOOTLOADER` | чем грузится устройство: `systemd-boot` (UEFI, по умолчанию), `extlinux` (U-Boot), `rpi` (прошивка Raspberry Pi), `android` (boot.img для ABL) |
| `DEVICE_TREE` | device tree устройства: `vendor/board.dtb` из `/usr/lib/modules/<версия>/dtbs` (или `vendor/` — пусть U-Boot выберет сам) |

Файлы, которые лежат рядом с профилем, указываются через `$PROFILE_DIR` — каталог читаемого файла профиля
(и у профиля из `inherit` — свой): `QUIRKS="$PROFILE_DIR/steam-deck.d"`. При смене профиля все эти переменные
сбрасываются. Рецепт, который упоминает такую переменную, зависит от неё: её значение (а для файла или каталога —
ещё и содержимое) входит в `buildid`, поэтому ядро для Steam Deck и ядро для ROG Ally — разные сборки в кеше,
а пакеты, которым GPU безразличен, общие.

Особенности пакета складываются по порядку: объявленные в рецепте (`+x` включена по умолчанию) →
`VIDEO_CARDS` профиля → `PROFILE_FEATURES` → `SPIN_FEATURES` подключённых сборок → `FEATURES` из `burn.conf` →
`package.features` сборок и `/etc/burn/package.features` → `-f`. Учитываются только особенности, которые рецепт
объявил. Особенности `video_cards_<карта>` (как USE_EXPAND в Gentoo) включает и выключает сам `VIDEO_CARDS`:
рецепт Mesa объявляет `video_cards_intel` и зависит от `llvm:video_cards_intel` — LLVM нужен для сборки,
только если в профиле есть Intel.

## Сборки (spins)

Сборка — то, что ставится поверх базы (DE, WM, киоск, …), в своём репозитории или каталоге:

```
spin.conf           что сборка ставит и включает (статический shell, как burn.conf)
packages/<имя>/     свои рецепты (необязательно): ищутся раньше рецептов базы
package.features    особенности отдельных пакетов (необязательно), формат /etc/burn/package.features
```

```sh
SPIN_NAME=labwc                          # необязательно: иначе имя репозитория или каталога
SPIN_DESC="labwc: лёгкий стековый Wayland-композитор"
SPIN_PACKAGES=(labwc foot labwc-spin)    # ставятся с зависимостями; настройки — тоже пакет
SPIN_FEATURES="wayland pipewire -x11"    # для всех рецептов, между профилем и burn.conf
SPIN_SERVICES=(seatd dbus)               # сервисы dinit, включаются при загрузке
SPIN_USER_SERVICES=(pipewire wireplumber) # сервисы dinit --user, включаются для каждого пользователя
SPIN_BASE=1                              # необязательно: самый старый уровень базы, на котором она работает
```

- `burn spin add <git-url|каталог>` — git-репозиторий клонируется (`--filter=blob:none`) в
  `$R/var/lib/burn/spins/<имя>`, каталог подключается ссылкой туда же. С этого момента рецепты сборки
  участвуют в поиске (после `-R`/`RECIPE_PATHS`, до репозиториев рецептов), её особенности — во всех
  `features` и `rid`. Затем ставятся `SPIN_PACKAGES` с зависимостями, пересобираются пакеты, которые стали
  несвежими из-за особенностей сборки (что было несвежим и до неё — дело `burn update`), и включаются
  сервисы: ссылки `$R/etc/dinit.d/boot.d/<имя>` и `$R/etc/dinit.d/user/boot.d/<имя>` (его ждёт
  `dinit --user` у turnstile) на файлы из `/etc/dinit.d` или `/usr/lib/dinit.d`. Сборка без рецепта для
  какого-нибудь из пакетов не подключается, как и сборка с `SPIN_BASE` выше `CLEANLINUX_BASE` из
  `os-release` корня (`/etc/os-release`, затем `/usr/lib/os-release`; нет поля — уровень 0): уровень
  контракта базы растёт, когда меняется то, на что сборки полагаются (имена пакетов и features, пути,
  каталоги сервисов).
- Что изменил `add`, записано в `$STATE_DIR/spins/<имя>`: источник, время, новые пакеты (всё, чего не было до
  неё, вместе с зависимостями) и включённые им сервисы.
- `burn sync` после репозиториев рецептов делает `git pull --ff-only` для каждой git-сборки (каталоги —
  забота пользователя). `burn plan` показывает пакеты из `SPIN_PACKAGES`, которых ещё нет (`new: spin <имя>`),
  `burn update` ставит их после основного обновления и записывает за сборкой.
- `burn spin remove <имя>` выключает её сервисы (если их не хочет другая сборка), отключает сборку (её рецепты и
  особенности пропадают), удаляет принесённые ею пакеты — кроме тех, что нужны чему-то ещё (пакетам
  пользователя или другой сборке), — и пересобирает пакеты, которым её особенности были нужны.
- `burn spin list` / `burn spin show <имя>` — сборки корня: коммит или каталог, описание, пакеты и их состояние,
  свои рецепты, особенности, сервисы, что принесла.

## Сборка

`burn build` (и `burn install <рецепт>`) проходит те же шаги, что прототип, и даёт тот же пакет байт в байт:

1. **Окружение.** Тулчейн, флаги профиля и пакета (`cflags_append`, `options=(!lto)`, особенности), ccache,
   `SOURCE_DATE_EPOCH` (последний коммит рецепта или самый новый файл его каталога), `buildid`. Пакет с этим
   `buildid` уже в кеше — сборки нет (`--rebuild` — есть).
2. **Источники.** Загрузка и проверка sha256 (как `fetch`), распаковка `tar`/`unzip` (кроме `noextract`),
   каталог исходников — `srcdir` или первый новый каталог; `patches` через `patch -Np<patch_strip>` (ищутся
   в каталоге рецепта, в `patches/`, среди загруженных файлов).
3. **Фазы:** `prepare` → `configure` → `build` → `check` (с `--check`) → `install` → `post_install`. Вывод —
   в `<кеш>/logs/<имя>-<версия>-<release>.log` (с `-v` ещё и на экран), при ошибке — последние 40 строк лога
   и код возврата фазы.
   - Есть функция `do_<фаза>` — её исполняет bash. burn пишет `WORK/env.sh`: конфиг, вводная часть
     (`src/prelude.sh`: `use`, `use_enable`, `meson_feature`, `run_fn`, …), сам рецепт, переменные сборки;
     каждая фаза — один `bash`, который читает `env.sh` и вызывает функцию.
   - Функции нет — шаг типа сборки (autotools, make, cmake, meson, cargo, python, meta, custom) burn выполняет
     сам: `fork` + `exec` с готовыми аргументами, без shell. bash нужен только, если в рецепте есть
     `configure_extra`/`meson_extra`/`cmake_extra`: их вывод — дополнительные аргументы.
   - `bt_configure`, `bt_install`, … внутри функции рецепта — тот же шаг в burn (`burn __bt`) с текущими
     значениями переменных и массивов (`make_args+=(…)` работает), а shell остаётся в том каталоге, где его
     оставлял прототип. Поэтому `do_install() { bt_install; …; }` работает как прежде.
   - **Изоляция** (`ISOLATE=auto`, по умолчанию). Каждая фаза — в своём сетевом пространстве имён: есть
     только `lo` (поднят — тесты слушают 127.0.0.1), наружу маршрута нет, так что сборка не может ничего
     скачать: всё, что ей нужно, — в `source` с sha256. Не от root burn для этого создаёт ещё и пространство
     имён пользователя (свои uid и gid отображаются сами в себя — файлы остаются твоими). От root фазы идут
     от `BUILD_USER` (`burn`, системный пользователь из пакета burn, без дополнительных групп): каталог
     сборки, её `HOME` (`WORK/home`), кеши cargo и ccache отдаются ему, `PR_SET_NO_NEW_PRIVS` не даёт
     вернуть права через setuid-программы. Пакет от этого не меняется: владельцы в нём всегда 0:0.
     Единственная фаза с сетью — `prepare` типа `cargo` (`cargo fetch --locked`, суммы из `Cargo.lock`).
     Что ядро не позволяет (нет пространств имён пользователя, root пространства имён без других uid —
     как в chroot стадии `native`), `auto` пропускает и говорит об этом одной строкой; `ISOLATE=1` в таком
     случае — ошибка, `ISOLATE=0` — без изоляции. Помощники `bt_*` вызывают тот же burn через унаследованный
     дескриптор его файла (`/proc/self/fd/N`): `/proc/PID/exe` родителя из нового пространства имён не
     читается.
4. **Чистка.** Merged /usr (`bin`, `sbin`, `lib64`, `usr/sbin`, `usr/lib64` переносятся в `usr/bin` и `usr/lib`
   переименованием), без `.la`, без `.a` рядом с `.so` (кроме `options=(staticlibs)`), без документации, info,
   man и лишних локалей по `FEATURES`/`LOCALES` (кроме `!prune`), `strip` ELF пачками (кроме `!strip`; `.ko`,
   `.o` и `/usr/lib/debug` не трогаются), предупреждение про `.a` из одних LTO-объектов, без пустых каталогов
   (кроме `emptydirs`).
5. **Пакет.** Split-пакеты забирают свои файлы (`files_КЛЮЧ`), опустевшие каталоги уходят; затем для
   каждого пакета рецепта — `.BURN/meta`, `files`, `provides-so`/`needs-so` (ELF разбирается в процессе), tar
   + zstd в процессе во временный файл и `rename()`. В кеше сборка есть, только если есть все её пакеты.

**Компилятор и PGO.** `COMPILER=clang` (в `burn.conf`) — родные сборки через `clang`/`clang++` и `llvm-ar`,
`llvm-nm`, `llvm-ranlib`; LTO тогда ThinLTO (`-flto=thin`), а линкер по умолчанию — `lld` (если `LINKER` не
задан). Рецепт, который clang не собирает (glibc, ядро), пишет `options=(!clang)` и остаётся на GCC. Cross-сборки
— всегда GCC (тулчейн bootstrap). `PGO=1` включает оптимизацию по профилю для рецептов с `options=(pgo)`:
сначала сборка с `-fprofile-generate` (`prepare`, `configure`, `build`), затем тренировка — функция `do_pgo`
(в `$SRC`, профиль пишется в `$PGO_DIR`), а если её нет — `check`; потом исходники распаковываются заново и
идёт настоящая сборка с `-fprofile-use` (GCC: `-fprofile-partial-training`, не покрытый тренировкой код
оптимизируется как обычно; clang: `llvm-profdata merge`). Тренировка без профиля — ошибка. Оба значения входят в
`buildid` (только когда включены: id сборок GCC без PGO не меняются). Воспроизводимость сборки с PGO —
не больше, чем у её тренировки: она должна быть детерминированной (тесты, фиксированный вход).

`burn unpack <пакет> [каталог]` — шаг 2 и `do_prepare`: исходники для правки или для bootstrap.

`burn install <рецепт>…` собирает недостающие и устаревшие зависимости по порядку (`--nodeps` — только
названные), спрашивает подтверждение (`-y`), ставит каждый пакет сразу после сборки. Зависимости сборки —
`depends` и `makedepends`. Когда инструменты сборки берутся с машины сборки (cross-сборка, `--host-deps`
в bootstrap), `makedepends` слоёв `devel` и `core` не собираются — они есть на машине (компиляторы, meson,
perl, python, openssl для ядра); `makedepends` остальных слоёв — заголовки и данные вроде `xorgproto`,
`wayland-protocols`, `tllist` — собираются и ставятся в корень: он и есть sysroot сборки. Если обновление убрало
SONAME, с которым слинкованы другие пакеты, старая библиотека сохраняется, эти пакеты пересобираются, и
сохранённая библиотека уходит.

Рецепты слоя `nonfree` — программы с несвободной лицензией (драйвер NVIDIA) — burn не собирает и не ставит,
пока владелец системы не разрешил это сам: `ALLOW_NONFREE=1` в `burn.conf`. Без этого и `install`, и `build`
останавливаются с лицензией пакета в сообщении — до сборки зависимостей.

### Подписи и бинарный кеш

Свои сборки можно брать с другой своей машины: настольный ПК собирает, handheld ставит. Пакет подписывается
ключом Ed25519; подпись — текстовый файл `ПАКЕТ.sig` рядом с ним:

```
burn-signature 1
file linux-7.3.1-8-x86_64-99f021bde54c.pkg.tar.zst
sha256 <sha256 пакета>
key desk
signature <128 hex: Ed25519 от первых четырёх строк>
```

Подписывается только это короткое утверждение: sha256 пакета burn считает сам (SHA-NI), а подпись делает и
проверяет `openssl` (`pkeyutl -rawin`) — он есть в каждой системе CleanLinux (TLS у curl), так что своей
криптографии в burn нет. Доверенные ключи — `$ROOT/etc/burn/keys/ИМЯ.pub`; имя ключа в подписи — имя этого
файла.

- `burn key new ПУТЬ/ИМЯ` — пара `ИМЯ.key` (0600) и `ИМЯ.pub`; `burn key trust ИМЯ.pub` — доверять ключу
  (копия в `/etc/burn/keys/`); `burn key list` — доверенные ключи и отпечатки.
- `SIGNING_KEY=/путь/ИМЯ.key` в `burn.conf` — каждая сборка этой машины сразу подписана; `burn sign [--key K]
  ФАЙЛ…` — подписать готовые пакеты.
- `burn verify ФАЙЛ…` — подпись есть, ключ доверенный, имя файла и sha256 совпадают, подпись верна.
- `BINARY_CACHES=(https://desk.lan:8080 /mnt/desk/packages)` — кеши пакетов своих машин (`https://`, `http://`,
  `file://` или каталог; раздавать можно любым статическим сервером, например
  `python3 -m http.server -d /var/cache/burn/packages`). Сборки, которой нет в своём кеше, burn сначала ищет
  там по имени файла — в нём `buildid`, то есть та же сборка: тот же рецепт, особенности, флаги, тулчейн и
  ABI зависимостей. Берёт её, только если все пакеты рецепта (split тоже) подписаны доверенным ключом, иначе
  предупреждает и собирает сам. Без доверенных ключей кеши не используются вовсе.

Путь корня в `buildid` не входит (флаги, которые лишь указывают на корень, — `-isystem /srv/deck/usr/include`,
`-L/srv/deck/usr/lib`, `-Wl,-rpath-link,…`, `--sysroot`, — не учитываются): ПК, собирающий для handheld в
`burn -r /srv/deck -p steam-deck`, даёт те же имена, что и сам handheld.

## Обновления (rolling+++)

- `burn sync` — для каждого `RECIPE_REPOS`: `git clone --filter=blob:none --branch $CHANNEL` в
  `/var/lib/burn/repos/<имя>`, дальше `fetch` + `checkout` + `merge --ff-only`. Ошибка git останавливает burn с
  кодом git.
- `burn plan` — каждый установленный пакет против рецепта: `upgrade`, `downgrade`, `rebuild` (тот же
  version-release, другой `rid`: изменились рецепт или особенности), а без действия — замороженные (`hold`),
  сироты (рецепта больше нет) и рецепты, которые не загружаются. Риски: `major` (сменилась первая цифра версии) и
  `core` (`CORE_PKGS`). Новые пакеты плана — то, что просят сборки (spins), и новые зависимости обновлений: то, от
  чего зависит новый рецепт обновляемого пакета и чего нет в системе (`new: dependency of burn` — так burn 0.7
  получил curl и git). Ниже — коммиты каждого репозитория с прошлого `update`, которые касались пакетов плана.
- `burn update` — `sync` (кроме `--no-sync`), план, подтверждение; сначала ставятся новые зависимости обновлений
  (как их поставил бы `install`: установленное не меняется, а сборкам они нужны в корне), затем загрузка и
  проверка всех источников и сборка всего плана в кеш — установленные пакеты не меняются, пока всё не собралось. Потом точка отката: снимок btrfs (ниже)
  и хуки `/etc/burn/hooks/pre-update.d/*` (упавший хук — `nothing was changed`), установка, ABI-пересборка, хуки
  `post-update.d` (их ошибка — предупреждение), запись состояния (`<repo>.commit`, `last-update`) и `doctor`.
  Исключение — рецепты с `options=(late)`: внешние модули ядра (NVIDIA) собираются против ядра, которое
  стоит в системе, поэтому их сборка ждёт, пока обновление применено, и идёт после ABI-пересборки, с установкой
  сразу после сборки. Если такая сборка упала, обновление остаётся применённым, а путь назад — снимок.
- Канал `security`. Рецепт перечисляет уязвимости, которые закрывает его version-release: `security=(CVE-2026-1234
  GHSA-abcd-efgh-ijkl)` (`lint` проверяет вид: префикс заглавными, дефис, идентификатор). `plan` показывает их
  строкой `security:` под обновлением; `plan --security` и `update --security` берут только такие обновления —
  без пересборок, без прочих новых версий и без новых пакетов сборок, — а то, что слинковано с ними, как обычно
  пересобирается ABI-шагом. Так устройство, которое обновляется редко (handheld в поездке), закрывает дыры, не
  принимая всего rolling.
- Снимок: если корень — подтом btrfs, `BTRFS_IOC_SNAP_CREATE_V2` делает read-only снимок
  `$ROOT/.snapshots/burn-<время UTC>` (несколько за секунду — `.2`, `.3`, …), старые `burn-*` сверх
  `SNAPSHOTS` (по умолчанию 5; `0` — без снимков) удаляются `BTRFS_IOC_SNAP_DESTROY_V2` (на ядрах до 5.7 —
  `BTRFS_IOC_SNAP_DESTROY`). Не btrfs — шаг молча пропускается, btrfs без подтома (`-r` в каталог) — с
  сообщением; ошибка снимка останавливает обновление до любых изменений. `burn snapshot` делает то же вручную.
  `.snapshots` может быть каталогом или отдельным подтомом (`@snapshots`) той же файловой системы; вложенные
  подтома (`@home`) в снимок не попадают. Каталог снимков читается заново после создания: btrfs не показывает в
  уже открытом каталоге записи, добавленные после его открытия.

## Установка пакета

Пакет читается одним потоком (zstd → tar) дважды: сначала только `.BURN/` — метаданные, список файлов,
проверка конфликтов с другими пакетами; потом содержимое.

1. **Распаковка рядом.** Каждый файл пишется в свой каталог под временным именем `.burn.<pid>.<n>`, получает
   владельца, права и время из архива; жёсткие ссылки, символические ссылки и устройства — так же. Новые
   каталоги создаются закрытыми (`0700`) и получают свои права в конце. Любая ошибка (кончилось место, битый
   архив) удаляет временные файлы — система остаётся какой была: `…; nothing was changed`.
2. **Подмена.** Временные файлы встают на место через `rename()`: в каждый момент на месте старый файл или
   новый, без полузаписанных. Файлы из `backup` — в три стороны, как в pacman: файл, который пользователь не
   менял (такой же, как в установленной версии, — её sha256 в `backup-sums` базы), получает новую версию;
   изменённый остаётся, а новая версия ложится рядом как `ИМЯ.burnnew`. При удалении пакета изменённый файл
   сохраняется как `ИМЯ.burnsave`, нетронутый уходит вместе с пакетом.
3. **Старые файлы.** Файлы прошлой версии, которых нет в новой, удаляются — кроме библиотек, с которыми
   слинкованы другие установленные пакеты: они остаются в `preserved` до пересборки (вместе с файлом, на который
   указывает символическая ссылка-SONAME). Сохранённые библиотеки, которые больше никому не нужны, удаляются
   в конце каждой команды; при удалении пакета уходят и его сохранённые библиотеки.
4. **База.** `syncfs`, затем новая запись базы собирается во временном каталоге и меняется со старой одним
   `renameat2(RENAME_EXCHANGE)`. Журнал пополняется после этого.
5. **Триггеры.** `ldconfig` и `depmod` (через загрузчик корня, если он есть) выполняются один раз в конце
   команды, а не после каждого пакета.

Все пути разрешаются внутри корня: `openat2` с `RESOLVE_IN_ROOT` (на старых ядрах — свой обход по
компонентам), поэтому ни `..` в архиве, ни символическая ссылка в корне, указывающая наружу, не выводят запись
за его пределы. Пути с `..` отклоняются ещё при чтении архива.

## Форматы (общие с прототипом)

### База установленных пакетов

```
$ROOT/var/lib/burn/installed/<имя>/
  meta          key=value: name version release arch chost [base] buildid rid profile summary
                license depends features backup cflags ldflags builddate (base — у split-пакетов)
  files         пути без ведущего '/', каталоги с '/' в конце, побайтная сортировка
  provides-so   SONAME, которые даёт пакет
  needs-so      SONAME, которые ему нужны и которых он не даёт сам
  preserved     старые библиотеки, сохранённые для тех, кто с ними слинкован
  backup-sums   «SHA256 путь»: содержимое каждого файла из backup в этой версии (только у burn на C)
$ROOT/var/lib/burn/state/history          дата|операция|имя|была|стала|прошлый файл пакета
$ROOT/var/lib/burn/state/<repo>.commit    коммит репозитория рецептов на момент последнего update
$ROOT/etc/burn/hold                       замороженные пакеты, по одному на строке
$ROOT/var/lib/burn/lock                   блокировка: один burn на корень
```

Команды, которые меняют корень, берут ту же блокировку, что и прототип (`flock` на `$ROOT/var/lib/burn/lock`),
поэтому две версии не работают с одним корнем одновременно. Пакеты перечисляются в побайтовом порядке.

### Пакет

`<кеш>/packages/<имя>-<версия>-<release>-<arch>-<buildid>.pkg.tar.zst` — tar (владелец 0:0, время файлов
не позже `SOURCE_DATE_EPOCH`), сжатый zstd. Первым идёт `./.BURN/` (`meta`, `files`, `provides-so`,
`needs-so`), за ним файлы относительно корня.

### Идентичность сборки

- `rid` — первые 16 hex-символов SHA-256 от рецепта, остальных файлов его каталога (в порядке путей) и строки
  features. Изменился `rid` — пакет пересобирается.
- `buildid` — первые 12 hex-символов SHA-256 от `rid`, `CHOST`, `CFLAGS`, `CXXFLAGS`, `LDFLAGS` (без флагов, которые
  лишь указывают на корень: где машина держит корень, для которого собирает, сборку не меняет), настроек
  чистки, переменных железа профиля, которые упоминает рецепт (`VIDEO_CARDS`, `KERNEL_CONFIG`,
  `KERNEL_FRAGMENT`, `KERNEL_CMDLINE`, `FIRMWARE`, `MODULES`, `QUIRKS`, `BOOTLOADER`, `DEVICE_TREE`; у файлов
  и каталогов — с содержимым), и SONAME
  установленных зависимостей; `COMPILER=clang` и PGO (`PGO=1` у рецепта с `options=(pgo)`) — только когда
  включены. Это имя файла в кеше: смена ABI зависимости никогда не подсунет устаревшую
  сборку. Переменные железа — расхождение с bash-прототипом: у рецептов без них `buildid` тот же.

## Файловые триггеры

Пакет может попросить burn запустить программу, когда транзакция затронула нужные ему пути: ядро в ESP после
установки ядра, hwdb после правил udev. Описание — файл `usr/share/burn/triggers/ИМЯ.trigger` в корне:

```
# пути — glob (fnmatch, `*` не выходит за каталог), одна или несколько строк
path=usr/lib/modules/*/vmlinuz
path=usr/lib/systemd/boot/efi/*
# программа из /usr/bin корня; $ROOT заменяется на корень («/» для живой системы),
# $ROOT/ПУТЬ — на путь в нём (/ПУТЬ для живой системы): run=/usr/bin/glib-compile-schemas $ROOT/usr/share/glib-2.0/schemas
run=/usr/bin/cleanlinux-boot --root $ROOT kernel sync
```

Описания читаются в конце транзакции, поэтому триггер, поставленный вместе с файлами, которые он отслеживает,
срабатывает и на них. Каждый триггер выполняется один раз за транзакцию — и при установке, и при удалении
подходящих путей, — после `ldconfig` и `depmod`, в порядке имён файлов. Программа запускается как `depmod`:
своим загрузчиком корня, если он есть, — так работает и установка в другой корень (`burn -r /mnt`). Ошибка
триггера — предупреждение, а не откат транзакции: файлы уже на месте.
